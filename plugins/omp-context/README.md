# omp-context

An omp extension that keeps the working set alive across context compaction.

## What it does

It tracks, per session:

- the user's last few messages, verbatim (at most 8, 1000 characters each), taken from `message_end` of a `user` message, i.e. the text as it entered the session. Raw `input` text is not used: omp chains input handlers (`runner.ts:1982-2005`), so another extension may rewrite or swallow it after this one saw it. Built-in slash commands, shell escapes and the `.`/`c` continue shortcut (a synthetic developer message, `input-controller.ts:985-998`) never become user messages, so they are not recorded. `/skill:<name> <args>` is the one exception: omp stores it as a custom message (`customType: "skill-prompt"`, `attribution: "user"`) whose content is the skill body and whose `details.args` is the user's own text, trimmed (`modes/skill-command.ts:63-87`, `extensibility/skills.ts:671-718`). The `args` are recorded verbatim as user words; the skill body and the whole draft (`details.prompt`, with the `/skill:` token) are not, and a skill invoked without args records nothing. In a plan-sdd run started with `/skill:plan-sdd <task>` this is the only place the task appears. Other user-attributed custom messages (for example omp's `collab-prompt`) are not recorded. File-based slash commands, custom commands that return text, and prompt templates do become user messages, with the expanded text (`extensibility/slash-commands.ts:124-141`, `session/agent-session.ts:7380-7397`); that expanded text is what gets recorded, cut to 1000 characters like any other message. Agent-attributed and synthetic user messages are not recorded;
- the active plan document (a `docs/plans/*.md` file that was read, written or edited, with any read selector such as `:raw`, `:5-10,20-30` stripped) and its `Status:` line: the first line that starts with `Status:`, plain or Markdown-bold (`**Status:** x`), shown as `Status: x` (the plan header); a task's `- Status:` line is not the plan's status. A ranged read, or a read without a `Status:` line, re-reads the status from disk and falls back to the previous status of the same plan; the status is taken only from omp's own `read`, `write` and `edit` results, so a plan changed outside them (a shell command, an editor) shows its old status until the model next reads or edits it;
- skills loaded: a `/skill:<name>` invocation (`skill-prompt` custom message), a `skill://<name>` read, or a read of `.../skills/<name>/SKILL.md`;
- git branch and worktree list (`pi.exec`, 3 s timeout), refreshed at `session_start`, at every `turn_end` and after each compaction. The `session_start` and `turn_end` refreshes run in the background and are not awaited (omp awaits `session_start` at startup and waits for in-flight handlers before it counts the session idle). Each refresh is numbered when it starts, and its result is kept only if no later-started refresh has already been applied, so a slow old answer never overwrites a newer one. The two git calls (`rev-parse --abbrev-ref HEAD`, `worktree list`) count separately, in three cases:
  - a call that succeeds replaces its own field (branch or worktree list);
  - a call that fails or times out (omp's `pi.exec` reports a timeout as `killed`, `exec/exec.ts:49-55`; a spawn failure, or any other non-zero exit) keeps the old value of its field, so a partial answer never drops the other field;
  - a definite "not a git repository" answer (non-zero exit with that message, not a timeout or spawn failure) clears the git info, so the block shows no stale branch or worktrees.

**After a compaction or rollover** (`session_compact`) it builds one restore block with that set, once per compaction entry id, and keeps it as the pending block. The block is set synchronously, before any `await`, from state already held (git and worktrees as of the last refresh), because omp may emit `session_compact` detached (`session-maintenance.ts:2490-2496`) and the next provider request can come before a git call returns. The handler then refreshes git once and fills in the git part of that block; the fill is dropped if a newer compaction has happened in the meantime. The block is delivered through omp's `context` event (documented in omp `docs/extensions.md:485`: `context` receives the conversation messages and may return `{ messages }`; source: `extensions/types.ts:1480-1482`, `runner.ts:2009`, `sdk.ts:4253-4256`): the extension returns `{messages}` with one synthetic user message inserted (see Placement), so it rides on every provider request (including mid-run steps and print mode, since `context` is called from the session's `transformContext`) until the next compaction replaces it with a block rebuilt from the then-current state. Nothing is persisted and no turn is started; `pi.sendMessage` is not used, because `nextTurn` waits for the next user prompt and `aside` at a post-turn compaction can wake a model turn nobody asked for. A second compaction with identical state still keeps exactly one block in place. After a rollover (`compaction.experimentalContextManagement` on) the block is thin: words, plan, git and worktrees only, since omp keeps skill and plan reads and already reminds the model to save notes.

Placement: the block is one synthetic user message (`timestamp: 0`, no `attribution`). The rule:

1. If a `compactionSummary` appears among the leading messages (scanning from the start past `custom` messages and synthetic user messages), the block goes right after it.
2. Otherwise it goes right after the earliest user turn: the first non-synthetic user message or user-attributed `skill-prompt` custom message (a `/skill:<name>` invocation), whichever comes first.
3. Otherwise nothing is inserted. It is never put at the tail or at index 0.

Why:

- After a rollover omp's `buildSessionContext` (`session/session-context.ts`) pushes the summary first (:540-545), re-appends the latest user request from before the compaction, which for a task started with `/skill:` is the skill-prompt custom message (:547-569), adds kept and later messages, and finally splices the `<experimental-context-notes>` custom message in at index 0 (:646-670). The real run in `docs/e2e/2026-10-16-omp-e2e.md` (item 3a) saw `[custom notes, compactionSummary, custom skill-prompt, custom todo reminder, assistant, toolResult, …]` with no `user` role, so a rule that only looked at index 0 and at user messages inserted nothing for 32 requests. That head stays fixed until the next compaction (`session-maintenance.ts:2466-2468` swaps it in once; later turns only append).
- omp builds its summarizer request from `convert(history)` and `convert(history + retained)` and cuts the second at the length of the first (`session/agent-session.ts:2380-2403`). A tail block would move that cut by its own size, could split a tool call from its result and would pull retained messages into the summarized range. The cut's history is the rebuilt summary plus entries after the previous compaction (`agent/src/compaction/compaction.ts:2051-2070`), so a leading summary sits at the same place in both conversions. Without a summary, the earliest user turn in history is also the earliest in history plus retained, and one only in `retained` lies after the cut. Either way the prefix is exactly `convert(history)`. Two looser rules would misalign: "after the summary only when there is no user message" (history alone puts the block after the summary, history plus retained after a user message in retained), and "user message first, skill-prompt second" (a skill-prompt in history, a user message only in retained).
- A block at index 0 would become the date/cwd reminder's root (`session/date-cwd-reminder.ts:66`). With a summary first the converted summary is the first user message, so that anchor is unchanged.
- Native Anthropic summary (`providerPayload.type === "anthropicCompaction"`): it must open the request, and the provider folds it into a directly following retained assistant turn whose signed thinking is bound to that prefix, so nothing may split the fold. Rule 1 then moves the anchor past that assistant turn, any `toolResult` messages after it, and the `<experimental-context-notes>` message if omp put it there. This is exactly where omp itself puts the notes (`session/session-context.ts:651-662`). The native cut only cuts where an assistant message meets a non-assistant one and never between a tool call and its results (`agent/src/compaction/anthropic.ts:137-171`), so the anchor is the same in history and in history plus retained.
- The timestamp is the constant 0 because a real one makes `flushCompactionFiles(msg.timestamp)` (`anthropic.ts:5869`, `ai/src/types.ts:1108-1130`) replay the summary's file metadata in front of the retained tail.

Prompt-cache cost: the block sits after the summary (or the earliest user turn). The `context` handler is synchronous over stored state, so two requests with no event between them carry the same bytes. The block changes once per compaction, at most once more when that compaction's git fill arrives, and when the nudge latches (its numbers are frozen then). What you pay is the block's size (a few hundred tokens) on each request until the next compaction, plus one effect of how omp treats it: omp marks every message a `context` handler inserts as per-call (`extensibility/extensions/runner.ts:2069`), and on Anthropic its cache-checkpoint placement only puts the every-15-user-turns checkpoints before the first per-call message (`ai/src/providers/anthropic.ts:4514-4518`). With the block near the start, those long-history checkpoints are effectively gone for the rest of the window; the trailing checkpoints still apply.

**During summarization** (`session.compacting`) it returns summary requirements as `context`: keep the user's words verbatim, plan status, open nodes, worktrees, pending decisions. It does not register `session_before_compact`, so omp's async speculative compaction stays on.

**Near-budget nudge** (legacy compaction mode only): decided at `turn_end` (settings and `ctx.getContextUsage()` are read there, never in `context`; this read is the only thing `turn_end` waits for) and stored. When `ctx.getContextUsage().tokens` reaches `nudgeFraction` (default 0.85) of omp's effective compaction trigger for the active model, a reminder (with the numbers frozen at that moment) is added to the same block on every request until the next compaction (it asks the model to restate key words, plan status and open decisions). A compaction clears the nudge and drops a decision still in flight, and nothing re-evaluates it before the next `turn_end`, so stale usage cannot re-arm it. No nudge when `compaction.experimentalContextManagement` is on (omp already reminds), when the mode or threshold cannot be read, or when compaction is disabled.

Mode and threshold are read from omp itself (`compaction.experimentalContextManagement` and `describeModelCompactionPoint`), so `compaction.thresholdPercent`, `compaction.thresholdTokens`, `compaction.modelThresholds` and the reserve-based default are all honoured. If those omp modules fail to load, the nudge stays quiet and everything else keeps working.

Every failure (git missing, no context usage, unreadable guidance file, throwing handler) degrades to a smaller block; nothing throws into omp.

## Install

Copy this directory to `~/.omp/agent/extensions/omp-context/` (or a project's `.omp/extensions/omp-context/`). `package.json` declares `"omp": { "extensions": ["./index.ts"] }`. No dependencies to install.

## Settings

- `compaction.experimentalContextManagement`, `compaction.thresholdPercent`, `compaction.thresholdTokens`, `compaction.modelThresholds`: omp's own settings; the extension only reads them.
- `OMP_CONTEXT_NUDGE_FRACTION` (environment variable): fraction of the threshold at which to nudge. Accepted only when it parses to a number with 0 < f < 1; anything else uses the default 0.85. A `nudgeFraction` passed to the factory beats the env.
- Session state is kept for the 32 most recently used sessions.
- `guidance.md` next to `index.ts` (so `~/.omp/agent/extensions/omp-context/guidance.md` once installed): the summary requirements text. When missing, empty or unreadable, a built-in default is used. The `evolve/` tooling replaces this file (see Evolve).

## Evolve (tuning `guidance.md`)

`evolve/evolve.ts` replays compactions found in omp session journals offline and keeps a new `guidance.md` only when it measurably helps.

```
bun plugins/omp-context/evolve/evolve.ts --sessions <dir> --bank <questions.json> --model <id> \
    [--target <dir>] [--rounds 3] [--samples 1] [--margin 1] [--dialect anthropic|generic] \
    [--baseline-file <file>] [--dry-run]
```

- `--sessions`: a directory searched for `**/*.jsonl` omp session journals. Each file is copied to a temp dir and the copy is parsed; the temp copies are removed when the run ends, on every path.
- `--bank`: recall questions (format and an example in `evolve/questions.example.json`). A fact counts as kept when its exact text, case-insensitively, appears in the new summary. A session is holdout when a `holdout` entry of the bank is a substring of its title or its file name.
- `--model`: generates both the candidate summaries and the candidate guidance, one request at a time, through `omp -p --no-tools --no-extensions --no-skills --no-rules --no-title --no-lsp --thinking high --system-prompt <file> --model <id> --session-dir <temp dir> @<prompt file> "<task>"` with stdin closed and the working directory a fresh empty temp dir. The prompt goes in the `@` file, which omp inlines into the message (omp skips files over 5 MiB, so a prompt over 4,000,000 bytes is left out of the run and reported). `--system-prompt` is omp's own summarization system prompt, passed as a file path. Evolve removes the temp files and directories it creates (its prompt files, session dir, working dir), also on SIGINT/SIGTERM/SIGHUP (the CLI kills the omp child, removes its temp dirs and exits 130/143/129 for SIGINT/SIGTERM/SIGHUP, after printing one line to stderr). What evolve does not touch: omp itself keeps one log under `~/.omp/logs/` and one session pointer file under `~/.omp/agent/custom-session-files/` per generator call, outside `--session-dir`; those accumulate in `~/.omp` and you may delete them.
- `--dialect`: `anthropic` drops thinking from the replayed conversation, as omp does for Anthropic models; `generic` keeps it. Default: `anthropic` when the model id matches omp's own rule for its anthropic class: `anthropic` or `claude` at the start of the part after the last `/` (followed by the end, `-`, `_`, `.`, `:` or a digit), or `anthropic` as a namespace part. So `claude4`, `claude-opus-5-5`, `x/claude4.5` and `anthropic/…` are anthropic; `my-claude-x`, `foo.claude-3`, `opus-5.5` and `kimi-code/…` are not. omp's per-provider overrides and tie-breaking between model classes are not mirrored. A short alias such as `opus-5.5`: pass `--dialect anthropic`.
- `--target`: where `guidance.md` is written (atomically: temp file in that directory, then rename). Default `~/.omp/agent/extensions/omp-context/` (from `$HOME`). Tests always pass a temp dir and a temp `HOME`.
- `--rounds`, `--samples`, `--margin`: integers of at least 1 (a bad value exits 2 with a message and does no work). `--samples` repeats each request and averages the score. Unknown flags, repeated flags, empty values and values starting with `-` also exit 2, as does a bank with an empty spelling or no `questions` array.
- `--dry-run`: run everything and report, write nothing.

A candidate is installed only when it keeps at least `--margin` more facts on the train conversations and no fewer on the holdout ones; otherwise nothing is written and the reason is printed. It refuses to run when either split has no cases, or when dropping failed cases empties one. A case whose prompt is oversize, or whose request fails at baseline, is dropped and reported; the run goes on. A candidate that fails on a case that passed baseline scores 0 on that case. A quota error, or a failing proposal request, stops the run with nothing installed. A candidate containing any answer from the bank is discarded unscored, and the next proposal is told only that a candidate was discarded for leaking, not what it said. Candidates over 2000 characters or containing `<` or `>` are discarded unscored. With few compactions in your journals, "nothing installed" is the honest result.

**Which compactions use the guidance.** The guidance reaches the summarizer through `session.compacting`. These compactions use it:
- `soft`;
- `remote`, including Anthropic native compaction, which formats the additional context into its instructions (`agent/src/compaction/compaction.ts:2116-2122`); non-native remote sends it too (`:1000`, `:1012-1016`).

A manual `/compact` is not a method of its own: it walks `compaction.methodOrder` like an automatic compaction (`session/session-maintenance.ts:1203-1228`): `remote` where the model can use it, then `snapcompact` only on an image-capable model when there is no focus text, then `soft`. So it uses the guidance when it ends on `soft` or `remote`. With `compaction.experimentalContextManagement` on, plain `/compact` (no focus text, no mode) is a rollover with no summarizer (`:1184-1188`) and uses nothing. (Pins, the sidebar section fed by `context_notes`, needs that setting.)

These do not use it: `handoff` (auto handoff writes its document without the context), `snapcompact`, `shake`, and a rollover. Evolve builds cases only from compactions with no `method`, `soft` or `remote`, and skips and counts (by method) `handoff`, `snapcompact`, `shake`, rollovers, and extension-supplied compactions (`fromExtension`, which omp stores without a method).

omp's default `compaction.methodOrder` is `remote, snapcompact, handoff, shake, soft`. On an image-capable model `snapcompact` therefore comes before `handoff`, and on a route without provider-native `remote` compaction an automatic compaction reaches `handoff` before `soft`: the guidance is not applied. To use it, put `soft` before `handoff` in `compaction.methodOrder`.

**With `compaction.experimentalContextManagement` on, the order above is not reached for automatic compaction.** Every automatic compaction then runs the rollover before `compaction.methodOrder` is read (omp `session-maintenance.ts:4680-4681`), so it never uses the guidance, nor anything evolve installs; plain `/compact` is a rollover too. What still reaches a summarizer with the setting on: `/compact <focus>`, and `/compact soft` / `/compact remote`, whose mode skips the rollover (`session-maintenance.ts:1184-1188`) and sets `methodOrder` to `soft` or `remote, soft` (`session/compact-modes.ts:42-52`). `/compact snapcompact` passes the rollover too but has no summarizer. Evolve builds its cases from the summarized ones. The setting is also what Pins (`context_notes`) needs, so the choice is Pins versus summary guidance on automatic compaction. The `soft`-before-`handoff` advice applies only with the setting off. The restore block does not depend on the compaction method.

**What the replay approximates.** Each case is the input omp's summarizer saw: the messages from the previous compaction's `firstKeptEntryId` (else the start) up to, but excluding, this compaction's `firstKeptEntryId`, with the previous compaction's summary (any method) as `<previous-summary>`, the guidance inside `<additional-context>`, then omp's own summarization prompt (copied into `evolve/omp-prompts.ts`). Known differences, so a score is an estimate of omp's behaviour, not a reproduction:
- the transcript uses plain role labels (`[Thinking]`, not omp's `[Think]`), not the per-model dialect renderer omp uses; tool results over 2000 characters are cut as in omp, but omp's filtering of contextually useless tool results (`agent/src/compaction/utils.ts:240-250`) is not reproduced;
- omp splits a long conversation into windows and clamps them to the model's budget (`compaction.ts:907-970`); evolve sends one request per compaction, and an oversize prompt is dropped instead;
- the request reaches omp as a `<file name="...">` wrapper around the prompt plus a short task message in the user turn, not as a bare user message; a literal `</file>` in a transcript is escaped so it cannot close the wrapper;
- omp's summarizer request has no tools and uses omp's summarization system prompt; the replay passes that prompt with `--system-prompt`, but omp still appends its own `<project-context>` block (workstation lines, context files, workspace tree) to a custom system prompt (`coding-agent/src/system-prompt.ts:1028-1036`), kept minimal here by the empty working directory; user-level context files omp loads from your home, and a global `APPEND_SYSTEM.md` that omp appends even with a custom prompt (`coding-agent/src/main.ts:1338`), are not suppressed by this tool;
- the start of the summarized window after a previous remote or V2 compaction is computed differently in omp (`compaction.ts:1356-1366`, `:1405-1416`); evolve always restarts at the previous `firstKeptEntryId`;
- when a turn is split, omp summarizes its prefix in a separate request (`:1462`); evolve inlines it;
- text other extensions add (`hookContext`, `promptOverride`) and the focus text of `/compact <focus>` are not reproduced.

## Tests

`bun test` (in this directory) drives a fake `pi`/`ctx` and temp directories; it never touches `~/.omp`. It also runs `evolve/evolve.test.ts`, which uses fixture journals under `evolve/fixtures/`, a fake generator and a fake `exec`; it never spawns `omp`.

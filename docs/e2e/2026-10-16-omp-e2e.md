## Findings (wrong or surprising behaviour in landed work), by impact

### F1. Restore block is dropped after a rollover when the transcript has no real user message (omp-context)

Evidence: item 3a. After the second automatic rollover (23:33:58) every one of 32 main-session requests up to 23:35:34 had `restore=0`; request starts `custom (<experimental-context-notes>)`, `compactionSummary`, `custom (skill prompt)`, no `user` role. The block came back only when I typed a normal message at 23:37:09. In a plan-sdd run the only user message is the `/skill:plan-sdd …` skill prompt, which omp stores as `custom`, so after the first rollover that leaves the block's anchor behind (the first rollover at 23:29:28 happened before any notebook existed, so there the summary was `messages[0]` and the block appeared). Code: `plugins/omp-context/index.ts:375-376` (summary only counts when it is `messages[0]`). The same anchor rule is documented for `plugins/omp-plan-memory`; I did not observe a plan-memory reminder falling in this window, so that part is unobserved.

### F2. Sidebar mouse cannot work with `tui.mouse: true`

Evidence: item 9a. Wheel and click inside the sidebar change nothing; the observer extension never receives SGR reports; core `#handleInlineMouse` consumes them first. The README sentence "Mouse routing is available when the host already enables mouse reporting" holds only for the fullscreen overlay path (not exercised); in the normal buffer, mouse reporting is enabled by `tui.mouse`, and that is the setting that takes the events away. With the setting off the sidebar handles wheel and click (item 9b), but a terminal does not then send them. Acceptance item 9 as written (`tui.mouse: true`, wheel scrolls, click runs the action, click outside not consumed) is not met; the "click outside not consumed" part also fails with the setting on (consumed by core, probe silent).

### F3. The user's own task statement is not in the restore block's words when the task came in as `/skill:…`

Evidence: item 3a, first restore block has no `Recent user words` section. `README` says slash-command text is deliberately not recorded; the effect in plan-sdd is that the one message that carries the task is never restored. Words appear after a later ordinary message (3b, 3c).

### F4. A low compaction threshold loops with this skill

Evidence: run 1 (`thresholdTokens: 30000`, journal `sess-run1-30k/…`): 18 rollovers in 2 minutes 10 seconds (23:26:03 to 23:28:13 UTC, counted from the journal) before the TUI printed `Warning: compaction: Compaction freed too little context to make progress — pausing automatic maintenance to avoid a compaction loop. The most recent turn alone is too large to reduce further; clear large tool output or switch to a larger-context model.` The skill's PLAYBOOK plus references are about 40K tokens read at start, above 30K. This is configuration, not a code defect; it is a limit for anyone copying `thresholdTokens` from `config.example.yml` with a small value. With 70000 two automatic rollovers happened, no loop, no compaction error.

### F5. Skill invocation: relative paths and calling convention cost the model several failed calls

Evidence: `read` results `Path 'PLAYBOOK.md' not found; resolved …` (omp corrected them) and four `bash plan_board_status` attempts before `write xd://mcp__plan_sdd_plan_board_status` (item 2, `probe/tool-timeline.txt`). Low impact; the run completed.
